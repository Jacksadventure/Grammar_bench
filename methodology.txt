Methodology for Grammar_bench
=============================

Abstract
--------
Grammar_bench is a novel benchmarking framework for assessing large language models (LLMs) and intelligent agents on software-engineering tasks centered around grammar parsing. Unlike static or manually curated test suites, Grammar_bench dynamically synthesizes fully randomized LL(1) grammars and implements corresponding recursive-descent parsers in Python. By introducing controlled mutations and deriving failure-inducing input instances, the framework measures model robustness and fault localization capabilities without risking overfitting to prepublished test cases.

1. Introduction
---------------
Evaluating the generalization and reasoning abilities of LLMs in software contexts remains a critical research challenge. Conventional benchmarks rely on fixed datasets, enabling model tuning or overfitting. Grammar_bench mitigates this risk by anonymizing and randomizing both grammar rules and parsers at runtime, ensuring each experimental trial presents an unseen grammar. The core contributions of Grammar_bench are:

- Dynamic Grammar Synthesis: On-the-fly generation of LL(1) grammars that satisfy parser-friendly constraints.
- Parser Auto‑Generation: Automated translation of abstract grammar definitions into working recursive-descent parsers.
- Targeted Mutation and Case Derivation: Systematic corruption of grammar rules to derive minimal failing inputs distinguishing correct and mutated parsers.
- Scalable Evaluation: Parallel test‑case mining and storage in a unified SQLite corpus for downstream model evaluation.

2.1 Design Principles
~~~~~~~~~~~~~~~~~~~~
- Anonymity & Randomization: No human‑designed grammars, eliminating dataset memorization (see README.md).【F:README.md†L4-L12】
- LL(1) Guarantee: Each generated grammar adheres to LL(1) constraints to enable deterministic recursive descent parsing.
- Reproducible Mutation: Controlled corruption with recordable mutation paths facilitates traceable failure analysis.
- Parallel Scalability: Workload distribution via multiprocessing accelerates case generation.

3. Grammar and Parser Synthesis
--------------------------------
Grammar and parser generation are co‑located in grammar_gen.py, which implements a four‑phase routine:

3.1 Random LL(1) Grammar Generation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
The function generate_random_grammar(num_nonterminals, ...) constructs a grammar that satisfies:

- No left recursion by design (productions never begin with their own nonterminal).
- Unique lookahead symbols: Alternatives for any nonterminal start with distinct terminals.
- Reachability repair: Ensures all nonterminals are reachable from the start symbol via BFS-based insertion.
- Optional right recursion controlled by loop_prob to simulate Kleene‑star patterns.

The algorithmic details—including nonterminal/terminal sampling, production carving, and reachability realignment—are fully documented in grammar_gen.py.【F:grammar_gen.py†L1-L160】

3.2 Example Derivation Extraction
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
To seed mutation validation, a small set of valid input strings is generated via generate_example_string(grammar, symbol, max_depth). This recursive routine traverses production trees up to a maximum depth, assembling terminal sequences that demonstrate grammar coverage.【F:grammar_gen.py†L160-L190】

3.3 Recursive‑Descent Parser Code Emission
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
generate_parser_code(grammar, nonterminals, start_symbol) compiles a full Python parser:

- Defines match(expected) and error(msg) primitives for token dispatch.
- Emits one parse_<Nonterminal>() per symbol, detecting iterative (star) patterns and inlining them as loops.
- Implements an entrypoint parse_input(input_str) with optional CLI main() scaffolding.

Parser generation logic, including AST pruning for unused functions, is detailed in grammar_gen.py.【F:grammar_gen.py†L190-L352】

4. Grammar Mutation Strategy
----------------------------
Controlled grammar corruption is performed by mutate_grammar(grammar, nonterminals, terminals) in mutation.py:

4.1 Depth‑Aware Mutation Targeting
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
A depth‑first traversal computes longest acyclic path lengths; the deepest nonterminal is chosen to maximize semantic impact. Production lists are shallow‑copied for mutation isolation.【F:mutation.py†L1-L60】

4.2 Symbol‑Level Mutation Mechanics
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
A random position in the selected production is replaced:

- If located at the lookahead (first) position, only alternate terminals are chosen to maintain LL(1) predictability.
- Elsewhere, any non‑self symbol (terminal or nonterminal) may replace the original.

The mutation step metadata—nonterminal index and production index—is preserved for biasing test‑case generation.【F:mutation.py†L60-L120】

5. Failure‑Case Derivation and Validation
------------------------------------------
The centerpiece of test-case mining is the generate_case(...) routine in main.py, which iterates mutation and input generation until reproducible parser divergences are found:

5.1 Biased Example Generation
~~~~~~~~~~~~~~~~~~~~~~~~~~~~
testies.py implements generate_biased_example(grammar, symbol, path, max_depth) that follows the recorded mutation path to bias expansions near the mutation site, then halts derivation immediately post‑mutation. This ensures minimal counterexamples.【F:testies.py†L1-L70】

5.2 In‑Process Validation
~~~~~~~~~~~~~~~~~~~~~~~~
compile_parser() from ultility.py dynamically loads parser code into the current process, exposing parse_input. validation_check_inproc(input_str, parse_fn) invokes the parser in-memory, catching SystemExit to classify acceptance or rejection without spawning external processes.【F:ultility.py†L20-L60】

5.3 Search Loop and Thresholds
~~~~~~~~~~~~~~~~~~~~~~~~~~~~~
For each corrupted grammar, up to MAX_INSTANCE_SEARCH attempts generate candidate strings. Only those accepted by the original parser and rejected by the mutated parser are retained, up to KEEP_TEST_CASES. If none are found within MAX_MUTATE_ATTEMPTS, the grammar is regenerated. Constants and control flow are defined in main.py.【F:main.py†L35-L110】

6. Data Storage and Scalability
--------------------------------
All mined cases are serialized into a SQLite database (targets6.db) via schema managed in main.py:

- Schema Initialization: init_db(cursor) handles table creation and schema migrations.
- Case Insertion: save_case(cursor, artefacts) performs transactional inserts, truncating oversized strings to avoid SQLite limits.

Parallel execution via ProcessPoolExecutor (worker count configurable) accelerates large-scale generation across parameter sweeps (dims, nonterminal_probs, loop_probs).【F:main.py†L300-L420】

7. Command‑Line Interface and Configuration
-------------------------------------------
The entrypoint main() in main.py offers a flexible CLI:

- Sweep controls: --dims, --nonterminal-probs, --loop-probs
- Grammar parameters: --num-nonterminals, --max-productions, --max-rhs-length, --nonterminal-prob, --loop-prob
- Search bounds: --max-examples, --max-mutate-attempts, --max-instance-search
- Parallelism: -w/--workers, -c/--cases-per-setting
- External‑grammar mode: --grammar-file

Default values are declared at the top of main.py.【F:main.py†L1-L34】【F:main.py†L240-L300】

9. Reproducibility, Anonymity, and Ethical Considerations
--------------------------------------------------------
By regenerating grammars at each invocation, Grammar_bench eliminates static vendor‑provided datasets, reducing overfitting risk. The fully anonymized grammars ensure that no proprietary or domain‑specific patterns are leaked, aligning with open science and ethical benchmarking practices.
